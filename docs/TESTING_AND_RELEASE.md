# 测试方案、性能与发布

本文件是项目验证范围、执行顺序、停止条件和测试完成标准的统一入口，由 [AGENTS.md](../AGENTS.md) 要求读取。修改代码、配置、资源、文档或执行验证前阅读；专项指南引用本文件，不再各自要求每次运行全量检查。用户明确要求的验证范围继续有效。

## 默认原则

- 日常修改默认定向验证；范围由行为影响和依赖关系决定，不由改动行数或文件数量决定。
- 先简短说明本次改动、影响范围和验证项目，再执行。常规测试选择不另设批准门槛；审阅或方案请求本身不授权修改。
- 覆盖本次要求的实际行为、相关边界和必要集成路径。验证通过且没有新风险后停止，不为“再保险”追加全量。
- 不以减少测试为由跳过必要的生成、运行时生效确认或发布验收，也不以存在全量入口为由默认扩大范围。
- 本规则立即用于选择验证范围；下文“工具后续改进”尚未实现，不能把计划中的参数写成当前可用命令。

## 验证分级

| 级别 | 适用情况 | 必须完成的范围 |
|---|---|---|
| L0 文档与静态检查 | 文档、注释、纯说明性调整 | 修改内容、相关引用与路径、UTF-8 无 BOM、LF；修改可执行命令示例时核对现有入口 |
| L1 定向验证（默认） | 局部 Bug、单项配置、单模块功能、局部界面或资源 | 直接相关的检查或测试，必要的生成与导入，能够证明本次行为的最小真实路径 |
| L2 关联回归 | 共享战斗逻辑、共享 UI、跨模块交互等影响可以限定的变化 | L1 加受影响消费者、边界和集成路径；不连带运行无关框架或界面测试 |
| L3 完整工程检查 | 基础契约或环境变化、影响无法限定、明确的完整阶段验收、打包发布 | 完整 `project.py check`；发布还需目标平台及最终制品验收 |

选择能够证明本次要求的最小级别。信息不足时先查调用链、数据消费者和现有测试；有新证据才扩大范围。仅编辑测试规则等说明文档属于 L0，不等于修改测试门禁实现。

### 常见改动对应范围

| 改动 | 默认验证内容 | 扩大条件 |
|---|---|---|
| 文档、注释 | 内容、链接、编码和命令准确性 | 内容实际参与生成或执行时检查对应链路 |
| 单项配置或数值 | 对应数据校验、生成结果、运行时实际读取与生效、直接相关边界 | 改变公共规则、schema 或多个消费者的行为 |
| 局部 Bug | 复现条件、修复后的同一路径、相关边界；有复发风险时保留回归用例 | 根因位于共享逻辑或发现关联失败 |
| 新增单模块功能 | 正常路径、关键边界、必要失败路径、一条真实端到端流程 | 改变其他模块的契约 |
| 文案或局部 UI | 对应界面的实际显示与操作；布局变化检查常用尺寸和受影响的边界尺寸 | 修改共享控件、字体、主题、输入坐标或伸缩策略 |
| 资源替换或图集重排 | 相关台账、引用、生成与导入、实际消费者显示 | 多个消费者共用资源，或改变导入与绑定规则 |
| 共享伤害、索敌、弹体等逻辑 | 受影响英雄、技能、目标类型和战斗路径 | 波及基础执行契约或无法限定消费者 |
| 胜率或概率调优 | 配置及实际行为校验；要求统计结论时增加相应样本验证 | 用户目标涉及胜率、概率分布或长期稳定性 |

例如：修改火球伤害时验证配置读取、实际伤害及相关增伤关系；修改共享伤害公式时覆盖受影响的伤害类型和英雄。修改一段说明不自动触发全英雄、所有关卡或多轮完整战斗。

### L3 的触发条件

出现以下情况时执行完整工程检查，并补充与变化直接相关的专项验证：

- 修改 foundation/runtime 的公共执行语义、Action/Command/Hook、状态所有权或跨 Feature 契约。
- 修改 RNG、Save 契约，或公共数据格式/schema 及其编译、校验契约。
- 升级 Godot、影响运行的依赖，或修改全局启动、加载及平台行为；单改窗口标题不因此升级。
- 修改构建、导出、测试选择或门禁实现，可能影响整个工程的结果可信度。
- 检查依赖后仍不能限定影响，或关联回归显示问题跨越原定范围。
- 用户明确要求全量验证、完整阶段验收，或本次交付包含可运行导出包。

不能仅以“新增了功能”“修了 Bug”“改了配置”“本轮即将结束”作为全量触发理由。高风险变更通过测试不替代 [AGENTS.md](../AGENTS.md) 规定的 ADR。

## 执行顺序与停止条件

1. 确认任务范围、当前改动和已有验证证据。首次需要运行工程且尚未确认环境，或引擎、Python、路径发生变化时执行 `python -X utf8 tools/project.py doctor`；纯文档任务不要求运行，已确认且未变化的环境不重复检查。
2. 选择 L0–L3，列出需要验证的行为、对应检查和不涉及的主要范围。由当前源码和实际消费者判断，不依赖必须存在 Git 仓库或自动 diff。
3. 按需准备输入：源表变化运行 `data`，资源或绑定变化运行相关生成及 `assets`，Ability Graph 源变化运行 `graphs`。不得手改生成物；文档、普通代码修改不无条件重建所有生成物或清空缓存。
4. 先运行能够最快发现本次问题的检查，再完成相关领域和真实交互验证。新资源、导入参数或缺少必要缓存时进行导入；日常工作不把清缓存和干净导入设为固定步骤。
5. 失败后先定位根因，修复后重跑失败项及受修复影响的检查。同一任务内输入、相关依赖、测试实现和环境未变的已通过检查不重复执行；无法确认是否变化时重跑受影响范围。
6. 所选范围全部通过、真实行为有证据且没有未解决的相关风险后停止。后续又修改了文件，只重新评估受影响范围。新增文档或测试报告不自动触发再跑全量。

测试数量和运行时长不是完成标准。出现未通过或无法执行的必要检查时，报告具体阻塞及未证实行为，不宣称完成。遇到无关历史失败应单列说明，不擅自修复、删除或绕过它来制造通过结果；完整检查失败仍须明确报告失败。

## 测试内容与证据要求

- 正常路径与直接相关边界必须可验证。非法输入、取消/失败、重复触发、对象失效仅在相应行为存在时覆盖；随机复现和 Save 恢复仅在涉及对应契约时要求。
- 简单、可逆的文案、间距或配置改动不为凑数量新增镜像式测试；能复用现有测试时优先复用。业务逻辑 Bug 优先补充可复现原问题的回归用例。
- 纯领域变化可用领域状态和事件证明；涉及场景连接、UI→Intent、资源、时序或清理时，增加对应真实 Scene/输入链验证。
- 启动无报错只证明启动路径，不证明战斗、交互或视觉正确。截图只证明可见状态；交互变化必须验证实际操作和结果。
- 布局或输入坐标变化按受影响尺寸检查；全局适配变化覆盖相关矩阵。完整平台矩阵属于发布或明确的适配任务。
- 运行进程必须同时检查退出码与输出中的 `SCRIPT ERROR:`、`ERROR:`、`TEST FAILURE:`；退出 0 不能掩盖错误。定向测试不得选中零项后报告通过。
- 报告实际执行范围、结果、必要证据位置及未执行范围；定向验证通过不能写成“全项目通过”。可测量时记录命令或阶段耗时，区分单阶段和总耗时，不凭断言数量估算速度。

简短报告示例：`L1：火球数据校验、对应领域回归及实际伤害确认通过；未运行其他英雄 UI、全量检查和导出，原因是本次未涉及这些路径。`

## 当前可用入口

下列入口按需组合，不是一份每次全部执行的清单。Godot 可执行文件沿用项目已确认的路径；涉及引擎 API 或版本行为时按 [官方文档规范](OFFICIAL_GODOT_DOCS.md) 查询。

| 目的 | 当前入口或方法 | 范围说明 |
|---|---|---|
| 修改文档检查 | 只读取本次文档及其相关链接，核对编码、换行和内容 | 不默认执行遍历整个工程的 `delivery_check.py` |
| Defense 数据校验 | `python -X utf8 tools/defense_pipeline.py check` | 校验当前 Defense 数据；现有管线未必支持逐表筛选 |
| 通用数据校验 | `python -X utf8 tools/content_pipeline.py check` | 按涉及的数据管线选择 |
| 资产校验 | `python -X utf8 tools/asset_pipeline.py check` | 按资源变化选择，不默认附加全套 Python 测试 |
| 指定 Python 模块 | `python -X utf8 -m unittest tools.tests.test_defense_fire_terms -v` | 示例为火焰词条测试，其他任务选择对应模块、类或方法 |
| 指定 Godot 行为 | 检查并复用 `validation/defense/` 中与任务匹配的定向入口 | 先核对其实际调用、当前数据前提、断言和退出语义；历史入口不自动代表当前覆盖完整 |
| 共用战斗测试场 | `python -X utf8 tools/battle_lab.py test --suite controls`，或 `case --case <JSON>` | 支持显式 controls/cases/heroes/ui/coverage/profile；范围、配置和证据边界见 [战斗测试场](BATTLE_LAB.md)；不替代其他模块的完整门禁 |
| 缺少 Godot 定向入口 | 在获准实施的任务中补充调用相关套件的最小测试入口，或做对应真实运行验证 | 不假设每个 `tests/test_*.gd` 都能直接用 `--script` 启动；不因缺少筛选参数直接改跑全量 |
| 架构检查 | `python -X utf8 tools/architecture_lint.py` | 按依赖、状态访问或模块边界变化选择；该工具目前全局扫描 |
| 启动烟测 | 当前 `project.py` 使用 Godot 的 `--headless --language en --path <工程目录> --quit-after 5` | 可按同样参数单独启动并检查错误输出；不替代界面或战斗验证 |
| 完整工程检查 | `python -X utf8 tools/project.py check` | 仅 L3；包含数据、资产、交付文件、Python、架构、Godot 导入/领域/Scene、release manifest 与启动烟测 |

当前 `project.py test` 仅比 `check` 少最后一次启动烟测，仍执行大部分全量检查；`tests/test_runner.gd` 也尚无套件筛选。不要把二者当作日常快速测试入口。

定向验证不要求刷新 release manifest。独立执行完整检查前，先完成本次确有变化的生成步骤，再用 `python -X utf8 tools/project.py release` 生成当前发布输入清单，然后执行 `check`；清单生成不等于测试通过，不得借此掩盖数据或资源漂移。

## 重型验证与性能

- 大量 seed、全关卡模拟、长时间运行、压力测试、完整截图矩阵只用于对应统计、稳定性、性能或适配目标，不自动附加到普通功能修改。
- 调整普通数值时验证该值实际生效；只有要求胜率等统计结论时才进行相应样本验证，并说明种子、策略、样本量和结论边界。
- 性能修改使用代表场景、目标硬件与实体数量，比较变更前后耗时或资源占用；新增大量怪物的目标不能只测当前低负载场景。
- `quality_budgets.csv` 是预算配置位置，示例阈值不是已经验证的项目结论。需要时定义 frametime、内存/显存、加载、包体、纹理、音频、对象增长等对应预算。
- 阶段或夜间验证可承担重型检查，但本规则不自动创建定时任务。未实施的自动化或未执行的检查不能作为已通过证据。

## 发布与完整阶段验收

发布继续遵守 [PACKAGING.md](PACKAGING.md) 与目标平台规则；Web 颜色和字体验收见 [WEB_EXPORT_PARITY.md](WEB_EXPORT_PARITY.md)。定向验证通过不能替代发布门禁。

- 导出前确认目标、分辨率、伸缩策略和适配矩阵，执行目标 profile 检查。
- 现有 `package.py candidate/export` 会清除引擎缓存、重建数据/资产/release manifest，并在内部执行完整工程检查。直接走该流程时不在外面先重复跑一次相同的 `project.py check`。
- `candidate` 和最终 `export` 各自包含的干净构建及完整检查仍保留。每次导出必须绑定本次输入与工具环境，不复用旧输出；不得因候选包通过就手动跳过最终导出门禁。
- 校验发布输入、源指纹、制品哈希和归档结构，并用最终制品验证启动、相关交互及目标适配矩阵；工程内通过不等于导出包通过。
- 记录版本或源指纹、Godot/依赖版本、数据和资产清单、测试结果及制品 SHA-256。按发布渠道补充许可证、符号/崩溃资料、签名、安装器或商店信息。
- release allowlist 排除源素材、编辑器、测试及工具等非运行时内容；以当前 preset 和清单校验结果为准。

需要完整阶段验收时执行一次覆盖最终状态的完整检查；同一状态已有可核对的完整通过证据时不为写总结重复执行。发布导出的干净构建要求不受此条豁免。CI 若后续接入，应区分日常定向检查与完整阶段/发布门禁。

## 工具后续改进（尚未实施）

本次仅建立规则与文档引用，不改变测试脚本。后续工具改进按最小可用范围实施：

1. 为现有入口增加显式选择 Godot/Python 套件、独立烟测和每阶段耗时；保留 `check` 的完整含义。
2. 仅加载所选套件及必要依赖，统一检查退出码和错误标记；未知名称、零项选择必须失败。
3. 校验指定套件确实执行、无关套件未执行、失败能正确上报，完整入口仍覆盖现有套件和嵌套回归。
4. 首版使用显式范围，不要求 Git，不引入复杂自动依赖分析、跨任务结果缓存或新测试框架。先得到耗时数据，再决定是否需要进一步优化。
